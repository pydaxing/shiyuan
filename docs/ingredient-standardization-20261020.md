## 用量规则

- 原文明示的单一数值和可确认单位转换为 `quantity` 与 `unit`，例如 `1勺`、`半瓶`；不同时保留 `amountText`。
- `原文未注明`、未写清用量等使用 `quantity: null`、`unit: ''`、`amountText: '适量'`。
- 明确表示少量的文字归为 `少许`。不擅自把一勺、一碗或一包换算为克数。
- 区间、按口味调整和缺单位等不能确定单值的表述使用 `适量`，不取假定中值。原文完整保留在来源记录及备份中，并不表示原区间仍显示在结构化用量栏。
- 只有原文做法提供明确依据时才修正明显错单位；多食材分别给出用量的，拆成独立项目，仍受 30 项上限约束。
- 新增 `头、段、滴、撮、盘、泵、副、芽、小勺、大勺、铲勺`。所有单位在前后端共用配置，家用容器单位不参与重量或容量自动换算。

## 新旧版本兼容

当前代码的请求使用 `ingredientUnitsVersion: 2`，读取标准数值和单位。未声明该版本的旧客户端读取新增单位时得到等值文字，例如 `0.5 头`，避免旧单位校验阻止编辑。旧客户端保存时，服务端将可确定的数值用量恢复为标准字段，数据库不会因此退回自定义文字。

新增单位的下拉选项需要包含该配置的客户端版本；本次不会自动发布正式小程序。旧客户端兼容并不等同于已经发布新客户端。

生产热修复基于实际下载的线上 `index.js`，只修改单位列表和请求兼容入口，保留本地尚未发布的其他功能。现有 Linux 依赖、云函数配置和存储权限不变。完整生产代码备份位于 `backend-before-live`。

## 执行顺序

1. `--scan` 只读备份；人工语义复核记录保存在 `semantic-review.json`。
2. `--prepare` 生成不可覆盖的完整计划和逐项前后对照。
3. 核对生产代码备份，仅增量部署 `unit-hotfix/kitchen-v2/index.js`；查询原部署任务，重新下载代码核对 SHA-256，不能把本地产物摘要冒充云端摘要。
4. `verify-ingredient-amounts-live.mjs --live --output artifacts/ingredient-standardization-20261020-verified-scan` 验证全部单位及旧客户端读写；临时测试菜谱必须精确清理，其他家庭记录必须不变。
5. `--apply --canary` 只更新一条美食并完整回读。
6. `--apply` 重新读取全范围，逐条条件更新、回读对照；家庭菜谱完成后刷新家庭版本。
7. `--verify` 最终只读校验，确认没有计划遗漏或非标准用量。

执行、验证均须传入上述 `--plan-digest`、备份中的生产 `--env` 和 `--output`。任何快照变化、未知写入结果或内容摘要不一致都会停止，不做猜测性重试。

## 暂停与回滚

- `write-reconciliation-required.json` 表示存在尚未确认的写入。必须查询其中原 `taskId` 并回读对应记录，确认结果后归档该标记；不得删除标记来绕过确认或重新发送未知结果的写请求。
- `--rollback` 仅在明确授权回滚后使用；按本次记录的标准化结果作条件匹配，恢复原食材数组，并拒绝覆盖后续人工修改。
- 不要先回滚单位兼容云函数再处理新增单位数据。必须先检查新产生的菜谱、库存及其他依赖，避免旧服务无法校验新增单位。
- 备份、计划、请求、回执与回读文件保留在同一目录，不应上传公开仓库或对外分享。
