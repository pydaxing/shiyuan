# 图片上传与邀请封面修复

## 已复现的问题

微信开发者工具内，用本地生成的 2400×3200 高纹理 PNG 测试旧压缩参数：

- 输入 25,766,538 字节。
- 目标长边 1400、质量 76：实际仍为 2400×3200，5,913,835 字节。
- 目标长边 1000、质量 50：实际仍为 2400×3200，4,358,961 字节。
- 目标长边 640、质量 30：实际仍为 2400×3200，3,674,614 字节。

因此，不能把 `compressImage` 返回成功视为已经完成缩放。原流程只尝试同一个压缩接口，缺少重新绘制图片的兜底。以上是模拟器复现，不能据此断言 iPhone 的每次失败都来自相同平台行为，也没有证据表明这是数据库性能问题。

## 修复方式

- 家庭封面、菜品封面、套餐封面、步骤多图、冰箱图片及微信头像共用 `compressNativePhoto`。
- 检查压缩结果的真实字节数、宽高和格式；要求不超过 480 KiB、长边不超过 1400，且为 JPEG/PNG。
- 原生压缩返回过大的图片、忽略尺寸、格式不兼容或失败时，使用微信离屏 2D Canvas 重新绘制并导出 JPEG。
- 显式指定导出的目标宽高，避免默认按屏幕像素密度放大；根据实际大小逐级缩小画面、降低质量。
- 清理不合格的中间文件并释放画布；保留原始选择文件，便于重试。多图保留共享并发上限 2 和部分失败重试行为。
- 旧设备无法使用离屏画布时，继续原生压缩重试；不放宽云端上传限制，也不上传未经验证的大文件。
- 网页端同样增加逐级缩小尺寸，保持现有数据 URL 长度限制。
- 邀请接口只返回用户设置的 `family.cover`；没有设置时返回空值，页面继续显示原来的餐桌插画。邀请凭证仍只能读取当前家庭封面的预览图。

## 第二轮修复：云函数请求超限

用户再次提供的截图明确报错为 `cloud.callFunction:fail Error: data exceed max size`。前一轮只验证了压缩结果，没有覆盖真机上的云函数传输限制，不能据此前一轮结果宣称上传问题已全部解决。

### 根因及修改

- 旧客户端仍把压缩后的图片编码为 Base64，通过云函数请求提交；411,391 字节图片编码后已约 549 KB，还未计算请求封装开销。图片符合服务端大小要求，不代表也符合客户端传输限制。
- 所有现有小程序上传入口统一改为：申请上传凭证 → `wx.cloud.uploadFile` 文件直传 → 用文件 ID 确认。包括家庭封面、菜品封面、步骤多图、套餐封面、食材图片、微信头像；小图也不再回退到 Base64 请求。
- 云函数请求只携带凭证、家庭 ID 和文件 ID；自动化测试中每次请求小于 1 KiB。头像上传不要求已经加入家庭。
- 保留压缩、真实大小/格式验证、加密存储和缩略图生成；没有放开云存储权限。凭证校验用户、用途、家庭、路径及有效期；同一凭证同一文件串行重试可返回已有结果。
- 图片缓存写入失败不再把已成功上传误报为失败，也不立即额外下载图片。传输异常不再直接展示 SDK 长篇追踪文本。
- 旧服务端 Base64 接口暂留给旧客户端和导入工具兼容；当前小程序上传不再调用它们。
