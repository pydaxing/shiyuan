# 本轮性能排查

## 结论

目前没有证据支持“空广场是因为数据库性能不足，必须升级数据库”。已确认的问题是请求链路有固定开销、前端重复等待、多个开关串行保存，以及图片压缩不保证实际字节大小。

本轮只部署按需启用的计时，没有改页面、缓存策略、开关保存策略或图片压缩行为。照片超限问题尚未修复，不应把本轮当作修复版让用户重新扫码。

## 测量边界

- 微信开发者工具通过真实微信身份调用已部署的 `kitchen-v2`，不是本地假数据库。
- 本账号 bootstrap 的 recipes、mealSets、orders、inventory、purchases、posts 均为 0，12 次广场查询也均为空。这不代表整个数据库没有用户、家庭、上传记录等数据。
- 耗时样本来自模拟器当前网络，不是手机 5G 的端到端实测；不能用它否定手机上的等待。
- 所有本轮带诊断的请求 `firstInvocation=false`。没有测到冷启动；不能把函数外耗时全算成冷启动或纯网络。
- `serverMs` 从进入函数 main 后开始；函数外差值还包括客户端 SDK、传输、网关、调度和可能的启动开销。
- 数据库计时包住数据库 SDK 调用，包括连接/通信时间，不等于数据库引擎的纯执行时间。
- transaction span 包含内部读写 span，不能把两者直接相加。
- 开关和家庭信息测量只保存即时读取的原值，每次带版本校验，发生并发冲突就停止，不重试覆盖。仍会增加家庭 revision、幂等回执及限流计数。
- 图片上传测量使用项目豆腐插图 28,272 字节，新增 3 个无业务引用的加密测试图片；文件 ID 已记录，没有上传用户截图或照片。

## 1. 空广场为什么仍然等待

真实云端共测 12 次：全部、菜品、荤菜、套餐各 3 次。

- 整次云调用：384～542ms。
- 服务端处理：98～187ms。
- `posts` 查询：31～74ms。
- 还需顺序读取用户和家庭确认成员权限，再执行 posts 查询。
- 以一次“全部”为例：总计 450ms = 函数内 98ms + 函数外 352ms；函数内为用户查询 37ms、家庭查询 30ms、分享查询 31ms。

客户端真实服务模块的受控复现还确认：

1. “全部”已经返回空，继续选择“菜品”“荤菜”仍另外请求，3 次操作产生 3 次请求，未共享已知完整空结果。
2. 请求完成前离开广场，响应不会写入缓存；返回页面又发一次请求。
3. 缓存按查询条件保存且只新鲜 30 秒，未完成请求没有跨页面合并。
4. 空缓存过期后刷新时，`ready=true/loading=true`，当前模板既不显示骨架，也不显示空结果提示，可能表现为短暂空白。
5. bootstrap 已读取首屏公开内容，但广场使用独立请求和缓存，没有利用该结果。

因此截图里的骨架是在等接口，不是数据库里存在四条未加载出的菜品。首次需要真实请求；重复进入或切换已知空分类的等待可以减少。不能将所有缓存一律永久设为空，仍需正确处理分页、搜索、新分享、删除和家庭变更。

## 2. 家庭开关为什么保存慢

真实原值保存各 3 次：

- 电子冰箱开关：643 / 673 / 1012ms。
- 我是大厨：758 / 793 / 1066ms。
- 修改家庭信息：1278 / 1377 / 1568ms。

单个开关并不是一次数据库写入：

1. 限流事务读写一次计数，并行读取幂等回执。
2. 再进入业务事务，顺序读取用户、家庭、幂等回执。
3. 写家庭及新版本，再写幂等回执，提交事务。

开关样本包含 2 次事务、8 次数据库读写；单次读写多数几十毫秒，叠加后函数内约 371～514ms。前端又把不同开关串行发送；受控复现中一次连点 3 个不同开关，最初只发送 1 个，全部完成需要 3 个依次完成。后面的开关会等待前面的保存。

家庭名称/封面标题还会经过文字审核，本次 371～570ms；这部分不是数据库写入。上一轮已做的乐观显示和局部回包仍在，但它们不会消除真正的事务、审核和网络等待。

## 3. 图片超限与上传等待

### 已确认的超限根因

当前微信客户端只执行一次 `compressImage({ quality: 70, compressedWidth: 1400 })`：

- 没检查输出实际字节数。
- 没有超过目标后继续降低尺寸/质量的流程。
- 只限定宽度，长图的高度仍可很大。
- 相册的 `sizeType: ['compressed']` 不是文件大小保证。

微信模拟器实际调用相同压缩 API，用重复纹理 PNG 做压力样本：

- 1400×2100：压缩后 JPEG 为 1,640,639 字节（约 1.56MiB），处理 192ms。
- 1400×6000：压缩后 JPEG 为 4,673,473 字节（约 4.46MiB），处理 326ms。

压力图是合成纹理而非手机实拍；输入 PNG 因重复纹理只有约 31KB/89KB，转换成 JPEG 后反而变大。这验证了“调用过压缩 API 不代表文件一定变小或低于上限”，不是对真实照片压缩率的估计。最初向自动化接口一次传大图片参数返回 HTTP 500；改用小段参数后完成上述压缩测量，该工具错误不等于小程序上传错误。

服务端 `checkImageBytes` 要求不超过 1MiB。超过约 525KB 的文件先申请票据、上传临时文件、再确认；确认时服务端还要下载文件检查，超过 1MiB 最后才报错。因此现状是“已经等了上传，最后还不能用”。不是简单增大数据库容量能解决，也不能直接放宽限制而不考虑审核 API 和响应大小。

### 真正成功的小图上传耗时

本次真实加密上传 3 次，总计 1564 / 1781 / 2198ms，不含选择和压缩。

以中间一次 1781ms 为例：

- 用户与家庭查询：约 59ms。
- 限流事务：156ms。
- 微信图片审核：604ms。
- 加密文件上传存储：274ms。
- 图片元数据写库：44ms。
- 函数外开销：643ms。

所以这次图片元数据写库并不是主要耗时；审核、存储、调用链路占大部分。审核和图片加密不能为提速直接去掉。三张图片均完成鉴权回读与字节一致性验证。

## 分步修复建议

1. **先修照片可用性。** 使用实际输出尺寸及字节数驱动自适应压缩，以最长边约束长图，目标不超过约 450～500KB；必要时逐步缩小并正确转换 JPEG。只有达到上限才上传；显示压缩、上传、检查进度。覆盖普通实拍、大尺寸、长图、PNG及 iPhone 真机。
2. **再修广场重复等待。** 利用已获取的可信首屏结果，缓存空结果，合并同查询在途请求；离开页面可以不更新 UI，但有效响应仍可存缓存；后台刷新不抹掉已有空状态。保留分页、失败重试及分享变更失效机制。
3. **再优化开关保存。** 维持即时反馈与失败回滚，合并短时间内不同开关的最终意图，评估安全合并部分事务，减少串行网络往返。保留成员验证、版本冲突处理、幂等和限流，不用“隐藏保存中”冒充加速。
4. **最后真机分段复验。** 记录点击到反馈、排队、云调用、函数内阶段及总耗时，对照 Wi-Fi/5G、首次与重复进入。当前证据不支持先购买数据库升级或预置实例。
