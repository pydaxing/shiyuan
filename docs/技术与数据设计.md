# 技术与数据设计

## 文字用量兼容（2026-09-10）

- 配方食材新增可选 `amountText`。数字配方继续使用 `{ name, quantity, unit }`；文字配方严格使用 `{ name, quantity: null, unit: '', amountText }`，文字非空、最多60字，不允许同时附带数字或单位。编辑、分享、广场导入及订单快照均保留该字段，服务端内容审核也包含该文字。
- 用量汇总按数字单位或原文用量区分；“盐5g”和“盐适量”同时存在时两项均保留。文字用量不缩放，需求的 `quantity/available/missing/toBuy` 为 `null`，通过 `needsConfirmation` 判断是否需要人工确认，不能用数值零代表未知。
- 采购点击文字项会要求确认已备好，使用 `recordPurchase` 保存 `kind: 'confirmation'` 的备料确认，仍走同一鉴权、事务与幂等接口。服务端推导当前关联订单及菜品签名，不接受客户端指定订单或伪造签名；新增餐食或相关菜品使旧确认失效，多位家人重复点同一道菜不会失效。
- 备料确认不是买入数量、不进入冰箱、不参与数字库存分配。完成餐食只扣减已知数量，未知用量不伪扣库存，关联确认随完成清理；取消或移出三天窗口不再产生采购需求。库存和实际买入依然必须是合法数字，计数商品购买仍向上取整。
- 原文采集转换保留“适量”“少许”等有意义文字，不能把空缺或明显错误数量自动填成“适量”。图片、主料完整性、来源授权及发布审核要求不变。新增用量数据需要配套更新手机端代码，不能仅部署服务端。

## 当前云端实现（2026-09-09）

- `src/domain/actions.js` 为本地与云端共用的业务动作。`src/store.js` 在 local 模式原子写设备存储，在 cloud 模式发送命令且只采用成功的服务端快照。不会读本机缓存充当云家庭。
- `server/application.mjs` 独立于微信 SDK，可注入事务仓储/时钟/审核/签名；`server/wechat.mjs` 接真实数据库事务、云存储、微信安全接口和可信 OPENID。测试仓储在 `tests/helpers/`，不打入云函数。
- 身份键为 OPENID 的 SHA-256；家庭成员内嵌 `families.members[]`，用户当前家庭记在 `users.familyId`。调用者、所属家庭、角色从服务端推导，不接受客户端切换身份。
- 菜品、套餐、订单、库存、采购分别在 `recipes/meal_sets/orders/inventory/purchases`，文档含 `familyId` 与 `value`；键按家庭 ID 和实体 ID 确定性生成。封面和开关在 families，日记由已完成订单推导而非造一份独立日历数据。
- `posts/comments/imports/reports` 保存真实社区内容、评论线程与用户点赞、去重加入记录、举报。帖子只公开经过内容检查的快照；删除原帖不级联删已导入配方及历史订单。
- 每条家庭命令在事务内获取最新家庭和实体；普通编辑须 revision 一致，避免覆盖；点餐允许在最新状态合并不同成员的选择。写入家庭 revision 使并发订单合并/完成串行化，状态变更和库存扣减一起提交。
- `requests` 保存用户作用域的请求指纹、家庭和返回值，支持网络结果不明的同请求重试；客户端同会话保留不同失败命令的键，不将所有错误当作未提交。客户端重启后仍须先同步核对不明结果，尚无跨进程重试队列。
- `server/validation.mjs` 白名单裁剪字段，限制层级/字段/大小，拒绝原型路径和数据库操作符；先校验再内容检查，餐次对象不能夹带 member/recipes 等字段覆盖可信输入。
- 所有客户端集合读写默认拒绝；图片先传临时区，服务端检查同一份字节并复制到 approved 不可改区。业务只保存批准文件 ID，经权限检查签发 5 分钟临时读取地址。完整权限和索引见 `deployment/`。
- 采购和厨房共用三天窗口：`shoppingOrders` 只保留 pending/accepted；完成、取消、跨天自动退出需求，但历史订单/开火记录不删除。库存与采购均以完整可买单位显示，做饭仍按配方标准量扣减。
- 客户端前台 20 秒同步、重进刷新；广场每页 30 条。家庭实体分页读取后合并为快照，上限每集合 10000 条，暂无大规模历史分页/全文检索/运营后台。真实环境容量、事务及规则还待联调。

当前有 15 个集合，名称与查询索引以 `deployment/database.json` 为准。部署、运营与未完成门槛见 [正式云端部署](正式云端部署.md)。

## 广场发布者与删除权限（2026-09-11）

- 官方导入的帖子使用独立 `publisherId: official:shiyuan`、`publisherType: official`，发布者显示「食愿小灶」；卡片与详情一致。不使用任何家庭成员的个人身份，菜谱原作者和来源继续保存在 `provenance`。
- 普通分享使用云端微信身份派生的 `publisherId` 和 `publisherType: user`。客户端不能通过菜品字段、分享参数或家庭名称取得官方身份。
- 仅本人发布的普通分享可删除。官方分享、其他成员的分享、缺失发布者的旧记录均不可删除；界面隐藏按钮，云端独立返回 `FORBIDDEN`。同一家庭的管理员身份不代表拥有其他人的分享。
- 用户将官方菜品加入家庭后获得独立菜单副本，可编辑、移除，也可作为自己的普通分享重新发布；不会覆盖、删除或变更官方原帖。
- 历史官方发布按可信批次回执的帖子 ID、来源 URL、家庭 ID 精确迁移。只修改帖子及 card 的六个发布者字段，不覆盖正文、评论、收藏、图片、分类、状态或已导入副本。已删除帖子不恢复。
- 本次前端更新升级广场列表与详情的缓存命名空间，防止沿用旧发布者；家庭及图片缓存保留。

## 0.6 分类、日记与本机身份

- `CATEGORIES` 为菜单、广场、编辑器唯一菜品分类枚举，包含其他。`matchesMenuFilter` 统一读取单菜 `recipes[0].category`，忽略旧广场 `categories` 主题标签；全类型下具体分类只筛菜品，套餐类型忽略分类。新发布单菜 categories 只含自身分类，套餐为空，不自动生成主题类目。
- `STOCK_LOCATIONS` 统一库存校验与编辑器选项。分区添加传 initial.location，全部入口回落冷藏，用户保存前仍可改位置。
- `cookingMonth` 为只读派生：从订单 `status === completed`、`order.date`、`meal` 和菜品快照构建周一开头月历。日数按日期去重、餐数按日期加餐次去重，同餐菜品按 recipe.id 去重。无额外存储表；菜品从菜单删除不影响日记。实际操作时间 completedAt 不代替用餐日期。
- 家庭成员无切换交互。`load()` 在旧订单迁移后将存在的本机 me 恢复为当前成员；保留原订单归属和发布作者，不在加载时落盘。内部成员切换方法仅用于本地领域测试，不代表鉴权能力；云端应以登录会话确定用户。

## 2026-10-20 分享防重复（覆盖下文历史重复发布规则）

- 同一家庭、源条目 ID、类型只能存在有效的一份发布；类型区分菜品和套餐，不按菜名去重。所有家庭成员共享发布状态，套餐内的菜品仍可单独分享。
- `sharedItems` 为可选快照元数据，每项包含 `kind / itemId / postId`，来自本家庭全部有效帖子，独立于分页美食流。缺失字段表示状态尚未知，不可迁移为默认空数组；旧客户端缓存自动重新获取。
- 前端「已分享」禁选与服务器事务守卫同时生效。重复请求返回 `ALREADY_SHARED`，不更新原帖、不重置统计，重试同一幂等请求仍返回原结果。该规则取代历史版本的“再次发布更新原帖子”。
- 删除权限不扩大；只有获准删除原分享后，该条目才恢复可分享。源家庭版本随删除递增，其他成员随后刷新状态；菜单、历史订单和已导入副本均保留。
- 部署索引见 `deployment/database.json`；本次只添加索引清单与代码，不擅自清理线上既有重复数据。

## 0.5 数据增量与交互

- `recipes[].nutrition?`：选填字符串，最多 500 字，保存时去首尾空白；空白不展示，分享白名单包含此字段。不自动生成医疗疗效承诺。
- 订单及成员选择的 `entries[].recipeIds[]` 保存套餐成员快照。`mealDishRows` 展开并去重，按套餐上色，一道菜可带多个套餐标签；后续修改/删除家庭套餐不损坏新订单的分组。旧进行中订单尽力从仍存在的家庭套餐补齐关系，无法恢复的关系不猜测；完成/取消历史不改写。
- `removeDishSelection` 从选中套餐移除菜品时，把剩余菜品转成单选；同时移除该菜的其他套餐来源，避免看似删除却仍留在本人的选菜清单中。提交仍只替换当前成员。
- `posts[].publisherId` 记录本机发布成员。同一成员重复发布同一菜单项更新自己的帖子；其他成员不能删除。旧无发布成员记录的本机帖子按家庭共有内容兼容删除。云端必须改为服务端鉴权，不能依靠客户端 ID。
- `comments[]` 增加 `memberId/parentId/replyToId/replyToAuthor/likes[]/createdAt`。回复的 parentId 指向根评论，replyToId 保存具体回复对象；点赞按成员 ID 去重，可取消。发布校验帖子和回复目标存在且同帖；本机所有更新仍原子保存。
- `deleteCommunityPost` 只移除当前发布内容与该帖评论，不操作 recipes、mealSets、orders，已经导入的家庭副本保留。
- 广场详情不再展示双统计；卡片用 `importedFamilyCount` 显示加入家庭数，没有云端数据时显示「—」。评论、回复、点赞和删除目前都仅限同设备。

## 0.4 基础规则（0.6 延续）

继续使用 `shiyuan-local-v1` / `version: 1`。读取时迁移内存副本，原存储只在后续成功提交时更新；存储失败保持原子回滚。

- `orders[].selections[]`：每位成员的 `memberId/memberName/entries/items/note` 快照。`entries` 保留菜品和套餐入口，`items` 保留菜品做法与标准配料。提交替换当前成员选菜，其余成员保留。
- `rebuildMealOrder` 将 selections 按 recipe.id 去重，构造 `items[].chosenBy[]`；每道菜 quantity 固定为 1，无 diners 和 scale，不按成员数扩大用量。已有菜品做法快照保持稳定，编辑菜单不改变正在备菜的配方。
- `submitOrder` 按日期 + 餐次 upsert 进行中订单。撤回最后一个成员时标取消并保留历史；完成后禁止再为这个餐次创建新订单。接受备菜后仍可更新选菜，完成时以最新需求检查库存。
- 旧 pending/accepted 记录合并，去掉倍率，重映射 purchases.orderIds，重复读取幂等；旧 completed/cancelled、库存及自定义配方不改变。
- `getShoppingRequirements` 保留精确 quantity/missing，新增 `toBuy`：全部餐次需求与库存分配完成后，再把缺口按根/个/只/盒/袋向上取整；g/ml 向上取整，kg/L 精确到 0.001。所有采购显示、复制和默认入库用 toBuy，做饭扣库存仍用 quantity。
- `removeFamilyEntry` 删除家庭菜单记录并修复套餐；少于两道的套餐移除。既有订单及广场帖子保持完整快照。删除库存批次重新计算采购。
- `family.members[].isChef` 默认为 false，开关只更新当前成员，独立于 fridge/shopping。
- `posts[]` 保存确认发布的快照、家庭名称作为 author、`familyItemId/familyKind` 作为本机来源关联。再次发布同一家菜单项更新原帖子 ID；不复制家庭成员/库存/订单，不执行网络传输。旧 JSON 分享模块保留作为内部字段白名单与兼容校验，不再提供粘贴/复制入口。

### 云端广场统计与发布待接入

目前卡片家庭数显示「—」，详情双统计已移除；不能用本机订单次数或 0 冒充全站数字。上线时新增 `community.publish / list / metrics`，以及鉴权的删除、评论、回复、点赞接口：先鉴权与内容审核，图片传云存储；菜品/套餐加入事件按 `(postId, familyId)` 去重。服务端返回加入家庭数与统计时间，客户端映射到 `importedFamilyCount`；断网或无结果仍显示无数据。删除公开帖子不得级联删除其他家庭已经导入的副本。

云端订单需要 `(familyId, date, meal)` 唯一约束、成员提交幂等键、事务合并及版本冲突检查。当前本机身份不是服务端鉴权，不能直接部署成多人后端。

## 0.3 本机数据增量（历史，以下倍率和分享方式已替代）

继续使用 `shiyuan-local-v1` / `version: 1`，`normalizeSnapshot` 只补缺失字段，不修改旧菜品、订单或库存，也不在读取时覆盖存储。

- `family.features: { fridge: false, shopping: false }`：两个独立开关，新家庭默认均关闭，已保存的手动选择保持不变。
- `mealSets[]: { id, sourceId?, shareId?, title, image, author, recipeIds[] }`：2～20 道不同家庭菜品，导入保持套餐，改菜不丢搭配。
- `orders[].diners`、`entries[]`：用餐人数及菜品/套餐入口快照。`items[]` 展开成配方快照与数量、`scale = diners / recipe.servings`。不原地改配方，不把大于上限的放大量写成基础配方。旧订单无 scale 时按 1 计算。
- `purchases[]`：冰箱关闭时的独立采购记录，含实际数量、单位、适用 `orderIds`；不冒充库存。做饭时消耗关联采购量并移除已完成订单引用；取消订单不参与计算，新订单不会复用旧采购记录。
- `getShoppingRequirements`：全部 pending/accepted 订单，按日期和餐次排序，逐一分配未过期库存，库存只使用一次。冰箱关闭时仅分配关联订单的采购记录。
- `shiyuan-share` v1：可复制的 JSON 图文分享，严格验证配方、图片、数量、类型、菜品 ID 和总长度。导出仅含选中的菜品/套餐，不含家庭、成员、订单、库存；本地图片转 data URL。重复导入不覆盖家庭修改，编辑后生成独立分享 ID。

当前没有公开发布接口。广场展示原创内置食谱，统计取自本地订单，不展示虚构全站加入家庭数。后续云端应保留以上契约，并补鉴权、作者身份、公开发布/审核和事务扣减。

## 技术选择

- 前端：uni-app / Vue 3，兼顾微信原生小程序输出和零账号浏览器体验。
- 当前：本地持久化仓储、纯函数领域逻辑；服务边界统一放在「家庭 → 关于与数据」。
- 计划后端：微信云开发的云函数 + 数据库 + 云存储，无自建服务器。
- 当前不引入支付、地图、外部账号、图床或公网 API，预览不上传家庭数据。
- 默认食物、步骤、食材插画和图标是项目内代码生成的静态 PNG，不依赖外部图片站点。用户图片仅本机处理：H5 压缩为 JPEG data URL，小程序保存持久文件路径，均非云上传。

## 云端集合（计划，不是已部署）

- `users`：平台身份关联、自填昵称、偏好、createdAt；身份键仅服务端处理。
- `families`：name、ownerId、timezone、settings、version。
- `familyMembers`：familyId、userId、role、capabilities、status；familyId/userId 唯一。
- `invites`：familyId、tokenHash、expiresAt、remainingUses、revoked；服务端验证并限速。
- `recipes`：familyId、title、category、baseServings、ingredients[]、steps[]、source、version。
- `mealOrders`：familyId、date、meal、selections[] 成员选菜、items[] 去重快照与 chosenBy、status、note、requestId、version。
- `inventoryBatches`：familyId、ingredientId、quantity、unit、location、expiresOn、version。
- `inventoryEvents`：familyId、batchId、delta、reason、orderId、requestId、actor、createdAt。
- `publicCollections` / `publicRecipes`：经过审核的公开副本，不直接公开家庭集合。
- `reports`：举报对象、原因、处理状态；只向授权运营人员可见。

索引：familyId+date+meal+status、familyId+ingredientId+expiresOn、familyId+userId；生产查询强制分页，避免全量拉取。具体索引语法待选定环境 SDK 后落地。

## 数量算法

1. 菜品定义标准配料用量；同日同餐多个成员选菜去重，每道菜仅计算一次标准用量。
2. 合并规范化食材名和单位维度。重量统一 g、体积统一 ml；计数单位原样匹配。
3. 全部未取消、未完成订单参与采购；跨日期/餐次按顺序分配库存，不重复借用同一批库存。
4. 可用库存只算未过期批次；未来餐次不抵扣提前过期的库存。精确缺口参与计算，采购另按完整计数单位或整克/整毫升向上取整；配方显示保留必要小数，近似显示标「约」。
5. 买入时新增批次，缺口重新计算；不是持久化一个容易过时的购物勾选状态。
6. 完成烹饪时校验当前库存，再按先到期先出扣减；状态与所有扣减一起提交，已完成重复请求返回明确错误，不再扣减。
7. 云端事务用服务端身份、版本和幂等键处理并发；当前本机版没有跨设备事务保证。

不自动换算个和克；不同维度分别提示。未来通过用户确认的每件净重转换，而不是 AI 猜测。不按人数或份数自动缩放配方。

## 本地持久化

存储键按版本命名。修改时先构造副本、验证业务、成功保存后再替换可见状态。解析失败时保留原始坏数据并报错，不悄悄覆盖为新示例；写入失败告知用户，不伪装已保存。演示成员共用本机家庭数据，只用来演示点餐来源。

未来需实现 schema 迁移、本机备份导出、云端冲突处理与多标签页变化通知。当前不要在多个浏览器窗口同时编辑同一家庭本机数据。

## 云函数契约（下一轮）

- `bootstrap`：获取当前身份和可访问的家庭摘要。
- `family.create / issueInvite / join / leave`：邀请申请、审批、角色管理、撤销。
- `recipe.list / save / import`：成员校验、输入校验、来源去重、图文安全。
- `order.submit / accept / cancel / complete`：拥有者/厨房权限、状态机、菜谱快照、幂等提交。
- `inventory.add / adjust / requirements`：采购与盘点审计、按餐次计算缺口。

客户端不得直接写管理员角色或库存余额。数据库默认拒绝跨家庭读写；公开内容与私有集合分离。错误返回明确代码，区分未登录、无权限、冲突、库存不足和服务暂不可用。

## 上线前安全验收

- 修改请求中的 familyId 不能读写别人的家庭；过期/撤销邀请不能加入。
- 普通成员不能发起管理员操作；退出家庭后旧页面也不能继续读取。
- 重放完成订单请求不会重复扣库存；两名厨师并发操作不会产生负库存。
- 云存储私有图不会通过猜 URL 暴露；删除菜谱后按保留策略回收资源。
- 日志避免输出 openid、私有备注、邀请令牌等；设置保留时长和最小访问权限。
- 真实社区开放前配置图文安全与举报；外部采购必须二次确认商品、金额和支付。
