# 食愿的推广与增长

资料核对日期：2026 年 10 月 28 日。产品功能以当前 [README](../README.md) 与实际微信版本为准；这份文档是执行方案，不是已经发布到各渠道、取得流量或完成埋点的记录。

食愿对外的小程序名称是 **食愿小灶**。推广首先回答一个问题：两个人或一家人每天反复问「今天吃什么」，能不能把选择、备菜与采购清单放在一个共同的地方？

## 先区分两种增长

| 目标 | 面向谁 | 希望对方做什么 | 应观察什么 |
| --- | --- | --- | --- |
| 小程序有人持续使用 | 一起生活、一起安排吃饭的人 | 微信搜索或扫码，完成一次家庭选菜与备餐 | 首次完成率、后续使用、具体反馈 |
| GitHub 获得关注与协作 | 对产品或实现感兴趣的开发者 | 看懂项目，下载研究，报告问题或参与改进 | 访问、下载、有效 Issue 与贡献 |

Star 是关注信号，不等于一个家庭已经开始使用。二维码也不能替代开发文档：普通用户需要立即进入产品，开发者需要知道项目怎样工作。

不承诺上榜或涨多少 Star，也不购买、互刷或用虚构评价制造热度。先让少量真实使用者完成一顿饭，再放大已经得到反馈的场景。

## 对外怎么介绍

推荐的一句话：

> 食愿小灶，把「今天吃什么」变成一家人一起完成的选择：挑想吃的菜、安排一餐、按菜备料，再整理采购清单。

名称要保持清楚：GitHub 项目叫「食愿」，微信内搜索「食愿小灶」。不要在海报、文章与二维码说明中交替使用多个小程序搜索名。

当前可介绍的能力包括家庭菜单、美食发现、餐食安排、备菜用量、采购清单、可选冰箱和开火日记。具体入口与限制见 README。

真实下单、支付、配送，以及 AI 选餐、搭配与健康分析，属于后续规划。可以解释想解决的问题，但不能写成当前已支持的功能，也不能承诺营养或健康结果。

## 从成熟项目中借鉴什么

以下是公开页面可观察到的做法；「对食愿有帮助」是应用这些做法的判断，不代表已经证明它们带来了项目热度。

| 参考项目 | 可以观察到的做法 | 食愿可采用的方式 |
| --- | --- | --- |
| [Mealie](https://github.com/mealie-recipes/mealie) | 产品定位清楚，提供文档、演示与问题反馈入口 | 首屏一句话说明用途，微信搜索和扫码入口靠前，开发文档独立可达 |
| [Tandoor Recipes](https://github.com/TandoorRecipes/recipes) | 围绕菜谱、计划与购物组织能力，提供安装、文档和试用入口 | 用「从选菜到备餐」串联介绍，让每一张图说明一件实际任务 |
| [HowToCook](https://github.com/Anduin2017/HowToCook) | 聚焦明确问题，内容组织便于查找，也有贡献入口 | 保持家庭共餐的定位，把可参与的真实改进写清楚 |

这些项目的受众、历史和功能范围不同，不直接拿其 Star 数量作为食愿的短期目标。尤其不能只增加徽章和图片，却让用户找不到试用入口。

## 推广前的仓库基础

以下项目需要按实际仓库状态核对；清单本身不代表已经完成。

- [ ] 仓库可公开访问，源码和历史中的敏感配置经过检查。
- [ ] README 首部有搜索名、扫码入口和一句话用途；尾部再次给出体验入口。
- [ ] 八张真实界面图保留，图注描述能完成的事情，手机边框不遮住内容。
- [ ] About 描述与 README 定位一致，Topics 与真实技术和用途匹配。
- [ ] 配置适合链接分享的 social preview，检查小尺寸时名称仍可读。
- [ ] 反馈入口清楚，Bug 与功能建议有模板，贡献指南可直接找到。
- [ ] 开发接手步骤、环境示例和版本记录可用，不把源码版本写成已上线版本。
- [ ] 明确代码使用许可；不要仅因为仓库公开就挂 MIT 或其他未采用的许可徽章。

GitHub 官方允许通过 Topics 描述用途与技术，并提供社交预览图、社区模板等设置。它们改善展示和参与入口，不保证获得推荐流量。

Topics 可以从 `wechat-mini-program`、`uni-app`、`vue3`、`cloudbase`、`meal-planning`、`recipe-management`、`family` 中选择实际匹配的词。不要添加尚未实现的 `ai` 或无关热门标签。

GitHub 社交预览图建议使用 1280 × 640，文件小于 1 MB。可放项目名、核心场景与少量真实页面；它首先要让别人愿意点开仓库，不宜塞满八张界面与细字。

## 宣传素材怎样使用

| 用途 | 优先素材 | 处理原则 |
| --- | --- | --- |
| README 体验入口 | 清晰的小程序码与搜索名 | 码和文字同时保留，适应电脑扫码与手机阅读 |
| GitHub 链接卡片 | 横向品牌封面 | 第一眼能读到「食愿」和用途；二维码不承担唯一入口 |
| 手机图文分享 | 竖向场景海报、真实界面图 | 一张图只讲一个场景，先痛点、再流程、最后体验入口 |
| 介绍长文 | 八张界面中的相关页面 | 根据文章内容选图，不为凑数量重复展示全部界面 |
| 打印或线下展示 | 高分辨率小程序码与海报 | 按实际成品尺寸检查清晰度，印前用微信试扫 |

二维码尺寸多不意味着每个场景都放一遍。优先保留高分辨率原图，按展示场景缩放；不变形，不裁掉码边缘，不在码上叠文字和装饰。

扫描是否能进入预期的小程序，需要实际微信核验。素材文件存在、图像清晰或 README 能显示，都不能替代这一步。

宣传截图使用已经获准展示的内容，公开前检查家庭名称、头像、邀请码等是否适合公开。不要为了拍图制造订单、评论、使用人数或其他虚假状态。

## 渠道与适配条件

| 渠道 | 适合讲什么 | 进入条件与边界 | 优先级 |
| --- | --- | --- | --- |
| 微信朋友圈或相关小群 | 一起决定晚饭、共享家庭菜单 | 作者自行分享真实场景，遵守群规，避免重复打扰 | 高 |
| 小红书 | 「今天吃啥」的生活场景与实际流程 | 图片清楚，名称可搜索，按平台当时规则处理外链与二维码 | 高 |
| 阮一峰科技爱好者周刊 | 有明确用途、可体验的中文独立项目 | 按仓库说明提交 Issue 自荐；是否收录由维护者决定 | 高 |
| 掘金等开发者社区 | uni-app、家庭协作、真实遇到的工程问题 | 文章要有可检查的实现细节，说明作者身份，遵守当时规则 | 中 |
| V2EX「分享创造」 | 作者亲自讲述已经做出的作品 | 先重读 About/FAQ；不要直接发布 AI 生成内容或批量搬运链接 | 中 |
| Hacker News / Show HN | 可直接体验、有技术或产品新意的项目 | 官方强调降低试用门槛；微信使用门槛使它暂不适合作为首发渠道 | 低 |

优先级是针对食愿目前形态的判断，不是这些平台的流量排名。微信、小红书和掘金的具体发帖限制需要发布当天再核对，不能把渠道名称当成自动获准发布。

V2EX 官方 About 写明不要发送 AI 生成的内容，FAQ 也反对注册后逐条搬运自己的旧链接。本文只提供本人撰写提纲，不提供可直接投放到 V2EX 的 AI 成稿。

本轮完善仓库和物料，不等于已向上述社区投稿或代发消息。每次对外发布都应明确账号、渠道与最终内容，并按当次授权执行。

## 可用文案与写作提纲

>
> 微信搜索「食愿小灶」即可体验。你家决定一顿饭，通常最纠结的是选菜、备料，还是买什么？

### 技术文章题目候选

- 把「今天吃什么」做成家庭协作小程序：从菜单到备菜的设计。

### V2EX 由作者本人填写的提纲

请用本人的经历和表达完成正文，不能把本文的推广草稿直接改名投到 V2EX。

## 14 天执行计划

从实际启动推广的当天算第 1 天。每一步都应以真实反馈推进，不因日程到了就多渠道刷同一条内容。

| 天数 | 具体动作 | 当天留下的结果 |
| --- | --- | --- |
| 1 | 核对仓库基础与微信体验入口，记录当前访问和使用数据 | 基础检查记录；没有权限读取的数据写「未知」 |
| 2 | 选择 3 张图讲清「选菜—备菜—采购清单」，准备短文案 | 一组可检查的场景物料 |
| 3 | 作者邀请少量愿意体验的真实家庭，自愿选择一顿饭试用 | 邀请渠道与人数记录，不收集不必要的个人信息 |
| 4 | 询问是否完成选菜、哪里停住；征得同意后记录问题 | 按实际步骤整理的反馈，不把建议当已发生行为 |
| 5 | 挑最影响首次使用的一个问题处理，按项目规则验收 | Issue、处理结论或明确限制 |
| 6 | 整理一篇产品介绍，注明当前能力与规划 | 可审阅的图文内容 |
| 7 | 作者选择一个生活场景渠道分享，记录发布时间 | 渠道、内容版本与链接；未发布则记原因 |
| 8 | 在后台权限允许时对照访问与关键行为，回看反馈 | 第一周复盘，区分点击与实际完成 |
| 9 | 准备周刊自荐材料，按当前模板核对后提交 | 投稿链接或待提交稿，不写成已收录 |
| 10 | 从真实源码选一个技术主题，写出取舍与可验证细节 | 技术文章草稿及对应代码位置 |
| 11 | 由作者选择一个开发者渠道发布，集中回复相关问题 | 一条有内容的技术分享及反馈记录 |
| 12 | 整理真实可参与的改进，补足重现步骤与验收目标 | 少量清楚的 Issue，适合时才标 good first issue |
| 13 | 回访第一批体验者，了解是否再次使用、为何使用或停用 | 经同意记录的原话与具体场景 |
| 14 | 比较渠道带来的使用质量，决定保留、修改或暂停哪种推广 | 两周复盘和下一轮一个明确目标 |

Bug 修复、数据库变更、云函数部署和小程序发布仍按各自流程完成。不能为了执行推广计划跳过真实验收，也不能把仓库更新当作微信已上线。

## 两类指标分开记录

### GitHub：是否被看见，是否能参与

| 指标 | 来源或方法 | 解读方式 |
| --- | --- | --- |
| 访问次数、独立访客 | 有仓库写权限时查看 GitHub Traffic | 看渠道曝光，注意它不是小程序用户数 |
| 克隆次数、独立克隆者 | GitHub Traffic | 代表工程获取，不证明成功运行或贡献 |
| 来源网站、热门页面 | GitHub Traffic 可用范围 | 用于判断入口；缺失来源不应强行归因 |
| 新增 Star、有效 Issue、外部贡献 | 仓库可见记录 | 分别记录，避免把三个行为合并为「用户增长」 |

GitHub Traffic 的访问与克隆统计覆盖最近 14 天。建议每周留一次小规模汇总，避免月底才回看时丢失早期变化；不要把暂无数据当作 0。

### 小程序：是否完成一顿饭，是否愿意再来

| 阶段 | 建议口径 | 当前如何使用 |
| --- | --- | --- |
| 到达 | 进入小程序的访问用户或访问次数 | 先确认微信后台可提供的指标与口径 |
| 家庭建立 | 新访客成功创建或加入家庭 | 需要可靠事件或后台可核验记录，不先假设已有报表 |
| 首次价值 | 完成选菜并形成一餐；另记是否继续备菜或采购 | 先定义成功动作，必要时在后续开发中补事件 |
| 再次使用 | 首次完成后第 7 天再次发生核心行为 | 样本不足、观察期未满时标注，不能提前报留存率 |
| 使用反馈 | 哪一步解决问题，哪一步让用户退出 | 自愿访谈可以补足数据，但不是统计结论 |

先核对已有统计能力，再决定是否增加埋点。不要为了追踪来源把个人资料、家庭内容或隐私写进公开 Issue；活动记录只保留所需的汇总。

## 每周复盘问四件事

1. 这周带来的是仓库浏览，还是完成了一顿饭的真实家庭？
2. 哪一个场景让人愿意试，哪一个步骤让人停下？
3. 哪条内容值得继续，哪条只是曝光高、使用少？
4. 下一周先改什么，才能让已有用户更愿意再来？

前两周的重点是找到能持续使用的场景。真正值得重复的推广内容，应该来自真实体验、可解释的产品取舍和持续改进记录。
