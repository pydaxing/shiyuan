## 一、构建正式包

在项目根目录创建 `.env.production`，将占位内容换成真实值：

```dotenv
VITE_DATA_MODE=cloud
VITE_CLOUD_ENV=你的实际云环境ID
VITE_CLOUD_FUNCTION=kitchen-v2
WEIXIN_APPID=你的正式小程序AppID
```

执行：

```sh
npm ci
npm run build:release
```

此命令先跑测试、构建云函数和微信端、检查原生输入及家庭入口，并执行 `scripts/check-native-images.mjs` 验证压缩后代码再转译为 ES5 的图片处理链路，再生成 `dist/release`。无正式 AppID 或无环境 ID 会直接失败。代码中的标识格式检查不能证明账号权限或环境确实可用。

微信开发者工具导入 **`dist/release`**。根配置分别指向 `miniprogram/` 与 `cloudfunctions/`，不会把云函数依赖打入小程序主包。不要导入原来的测试号目录，也不要将 `qa-not-deployed` 等验证占位环境用于手机预览。

生成手机二维码统一使用 `npm run preview:weixin -- --output artifacts/deployment/wechat-preview`。该入口固定使用 `dist/release`，先检查正式 AppID、云环境、云函数名称和产物是否为云端模式，再调用官方开发者工具。正式构建也会同步中间产物的 AppID，避免云端代码与测试身份混装；之后单独运行普通微信构建仍可能恢复测试身份，所以不能绕过这个预览入口。预览只生成体验二维码，不提交审核或公开发布。

## 二、建立数据库与权限

在**同一个云环境**的控制台按 `deployment/database.json` 创建 15 个集合：

`users`、`families`、`recipes`、`meal_sets`、`orders`、`inventory`、`purchases`、`posts`、`comments`、`invites`、`requests`、`media`、`imports`、`reports`、`rate_limits`。

每个集合都配置 `deployment/database-rules.json`：客户端读、写均为 `false`。包括广场和评论也不能直接开放读取，公开数据统一由云函数筛选，避免泄露已删除帖子和私有记录。管理员控制台和服务端 SDK 不受客户端规则限制，因此服务端还必须做成员鉴权。

`database.json` 是本项目的集合/索引清单，不是假定存在的控制台一键导入格式。按每个 `indexes` 数组的顺序创建非唯一升序复合索引，数组字段 `categories` 按当前控制台的数组索引能力配置；若环境提示某组合不支持，先停止发布并根据实际查询调整，而不是放开权限。`_id` 自带唯一索引，不重复创建。搜索是受限长度、转义后的文本匹配，面向早期小规模广场，不是全文搜索引擎。

2026-10-20 分享防重复更新：部署前补齐 `posts` 的 `familyId + status + _id` 和 `familyId + familyItemId + status + _id` 非唯一升序索引，分别用于完整分享状态的轻量分页和事务内查重。保留旧索引以兼容旧版本查询；不需要批量修改已有帖子。先准备索引并部署包含 `sharedItems` / `ALREADY_SHARED` 的云函数，再更新小程序；旧缓存会自动请求补齐状态。仅修改本清单或完成本地构建不等于这些索引已经在线创建。

订单合并依靠家庭文档的事务写冲突序列化，并在事务内查找日期/餐次；不是仅靠前端去重。幂等记录使用 `(用户, requestId)` 的确定性文档 ID。

保存链路按操作加载必需的列表；设置类不加载业务列表。事务内仍顺序执行，鉴权、限流、版本校验和幂等不取消。新客户端请求 `responseMode=changes`，服务端仅在本次事务基线与请求版本一致时返回变更；不满足条件、命中旧回执、发布分享或旧客户端则返回完整快照。客户端再次检查家庭及基线版本，不兼容时只刷新，不重复提交。变更列表保持数据库读取顺序，避免下一次刷新时重新排序。

## 三、配置云存储

当前环境保持默认 `PRIVATE`。`deployment/storage-rules.json` 是更严格的可选自定义规则，**免费环境没有部署成功，不能声称已生效**。实际测试发现 PRIVATE 下服务端上传文件可被客户端直接下载，仅依靠这个名称不能保护家庭照片。

- 小图（base64 不超过 700000 字符）通过 `mediaUpload` 单次传到云函数，验证 JPG/PNG 格式与大小后压缩、加密存储；不调用微信内容检测。大图或旧预览仍先上传到本人 `private/` 临时目录，通过 `mediaConfirm` 校验文件归属并处理。
- 使用随机独立密钥 AES-256-GCM 加密，保存为 `approved/家庭ID/随机ID.bin`，删除临时原图。`approved` 是兼容旧文件的存储路径，不代表内容检测结果。密钥仅在禁止客户端读取的 `media` 集合中保存，不返回客户端。
- 客户端读取图片通过 `mediaContent` 或最多 6 张一组的 `mediaBatch`。列表读取 `card` 压缩图，详情和步骤读取 `detail` 展示图；点击图片才读取已保存的高清图。服务端核验真实微信身份、当前家庭成员资格、家庭归属/已导入副本/历史订单引用或仍公开的分享，再解密返回图片内容。不向客户端发放可读原图的存储直链。各展示版本独立加密，密钥仍仅保存在服务端。
- 原作者删除分享后，未导入家庭不能继续通过该分享取图；已经导入的独立副本和历史订单仍可取图。成员移除后续请求拒绝。无法远程收回用户已下载或截图的内容。
- 前端最多并发 6 张展示图加载，并为点击后的高清预览保留优先通道；相邻请求合并，缓存最多 120 个版本、8MiB 在微信私有文件目录，5 分钟后重新校验权限。只加载可见区域附近的图片。上传最多并发 2 张，按选择顺序返回，并保留部分成功结果。手机照片上传前缩小至最长边 1400 像素、目标不超过 480KiB；服务端保存高清版本并生成列表/详情版本，不等同于保存未经处理的相机原文件。图片索引持久保存，重启后校验身份再复用同一用户/家庭的图片；切换/退出家庭清理当前缓存，仅清理旧格式和无索引的缓存文件，不删除用户草稿。菜品与步骤仍只保存文件 ID，不存 base64。
- 家庭快照缓存、广场分页缓存和详情缓存详见《本地缓存优化-2026-09-11》：已确认的家庭数据持久保存，冷启动先验证身份和版本；广场/详情命中缓存立即显示，过期后台刷新，不把网络失败显示成空列表。缓存不替代数据库，不绕过保存确认或成员权限。
- 真实验收：鉴权后解密字节与上传原图一致；直接下载存储文件得到 `SHIYUAN1` 密文而非照片；客户端覆盖和删除 approved 文件均被拒绝；客户端直接读密钥数据库失败。

云函数身份/家庭权限、密钥数据库规则与加密完整性必须一起保留。旧未加密测试图不做静默迁移，接口提示重传。公开前仍须用第二个真实微信号验收跨家庭隔离与移除后失权。**不要为了上传成功改成所有人可读写。**

官方参考：[数据库安全规则](https://docs.cloudbase.net/database/security-rules)、[云存储安全规则](https://docs.cloudbase.net/storage/security-rules)。

## 四、部署云函数

1. 在开发者工具中选择与前端环境 ID 一致的云开发环境。
2. 先运行 `npm run build:release`。正式包中的目录是 `dist/release/cloudfunctions/kitchen-v2`，与 `VITE_CLOUD_FUNCTION` 一致；源码构建仍输出 `cloudfunctions/kitchen`。图片处理依赖 Linux 原生库，**不要直接上传 Mac 的 node_modules，也不要沿用“云端安装依赖”作为已验证路径**。使用已授权的官方 CloudBase CLI，运行 `TCB_CLI="$(command -v tcb)" node scripts/deploy-cloud-verified.mjs --live`；若 `tcb` 不在 PATH，设置 `TCB_CLI` 为其实际可执行文件绝对路径。脚本打包锁定版本的 Linux 依赖、关闭云端依赖安装，并通过官方 API 部署。当前云端运行时已核实为 Node.js 20.19，构建目标为 Node.js 18。
3. 核对入口 `index.main`、超时 60 秒、内存 256MB。`config.json` 中 `permissions.openapi` 为空，不需要申请内容检测接口权限或恢复检测额度。云端历史授权是否保留不影响新代码，它不再调用这些接口。
4. 必须等待脚本确认函数为 Active，且云端 `CodeInfo` 的 SHA256 与本地构建一致；回执写入 `artifacts/deployment/image-delivery/backend-deployed.json`。仅 CLI 显示“成功”不足以证明代码已更新。再使用已登录的微信小程序实际调用并验证压缩图和多图上传。身份由云函数 `getWXContext().OPENID` 决定，不在测试 JSON 里伪造 OPENID 当作登录。
5. 首次进入应显示创建/加入家庭；创建后菜单、订单、库存为空，只有本人，不自动生成假家人、假评论或假采购。

分享与请求回执在同一个事务中保存，成功后即可公开；事务失败不会留下半发布状态。云存储、数据库或函数故障不会自动降级到本机存储冒充保存成功。

## 五、必须通过的双账号验收

使用 A、B 两个真实微信号与同一个体验环境；再用 C 的独立家庭测试隔离。

1. A 创建家庭，填名称/封面，创建两道带图片与多图步骤的菜，组合为套餐；重开小程序后仍在。
2. A 在「家庭成员」右边邀请，B 选择加入家庭并输入 12 位码。同一家庭数据可见，只有 A 可生成/轮换邀请码。码 24 小时有效，轮换使旧码失效，家庭上限 20 人。
3. A、B 同时点今天晚餐的相同菜及不同菜，只形成一单，菜品去重、选餐头像分别保留。前台每 20 秒刷新，重进小程序或手动同步立即刷新，不宣称毫秒级实时。
4. 关闭冰箱：未买齐也可备菜/开饭；完成、取消或日期滚出三天窗口后，采购需求消失；订单历史和日记仍保留。开启冰箱：缺货时不能误扣库存；买入、开饭扣减、重复点击均正确。
5. A 分享菜或套餐，C 从广场搜索、加入并自行编辑；C 发布评论、A 回复/点赞。删原分享不删 C 的菜单和订单快照。
6. B 不能移除 A、不能删除 A 的帖子；C 不能通过改 familyId、memberId、图片 ID、recipeId 读取或修改 A 家资料。移除 B 后，其下一次读取/写入失效。
7. 模拟弱网、提交后断网、重复点击、两个成员同时编辑。失败保留表单；结果不明的同会话重试沿用幂等键；版本冲突必须刷新并让用户确认，不能静默覆盖。**关闭小程序后，不明结果操作应先同步核对再重新提交**，客户端待重试键目前不跨进程保存。
8. 两台真机验证键盘、相册、滚动、触感、底部按钮与胶囊遮挡。网页自动化和编译检查不能替代这一步。

- 成员退出只需一次确认；管理员退出时，在同一事务内自动将管理权交给最早加入且仍在家的成员，最后一人退出则自动删除家庭。也可单独转交管理权并留在家庭。主动删除整个家庭仍需管理员输入完整名称确认。账号注销、历史数据导出/清除目前仍需授权运营人员处理，尚无自动化管理后台。公开前须明确处理渠道和响应责任人。
- 举报写入 `reports`，运营人员在受权限控制的控制台处理；违规帖子设 `deleted`，记录处理结果。尚无自动化举报处理后台，不能宣称举报后必定自动下架。
- 配置费用、错误率、超时告警、每日数据库备份并演练恢复。保留云函数版本以便回滚；先在体验环境验证，不直接在正式库试删除。
- `rate_limits`、过期邀请码、废弃上传票据及临时图片应由管理员按时间清理；`requests` 幂等收据不能随意删除，否则很久以前的重试可能再执行。图片清理须核对所有家庭副本、公开帖子及历史订单引用，不按原作者删除就级联删图。
- 当前家庭实体按集合分页读取但合成一个快照，单集合超过 10000 条明确报容量错误；这不是大规模社区的长期架构。2026-09-09已增加新客户端轻量广场16条游标分页、独立评论20条分页、按需详情和图片条件鉴权缓存，见《正式版性能优化-2026-09-09》。按日期拆分家庭历史订单、全文检索和长列表虚拟化尚未实施，扩量前继续按实测容量完善。

- 小象超市目前仅提供跳转/复制采购清单，未取得官方购物车/代下单接口，**不能一键真实下单**，不模拟成功。

## 本地数据与回滚

本地模式保留 `shiyuan-local-v1` 原数据；云端模式不会读取它，也不会无提示上传私人照片。旧菜单不会自动出现在云端，需明确选择迁移方案后再做导入，避免把示例家庭、历史测试单、设备图片路径混进正式库。

不连接云端时继续体验：`VITE_DATA_MODE=local npm run build:web`，再启动 `PORT=4174 npm run preview`。重新构建本地版不会改变已经生成的 `dist/release`。不要将本地包上传为正式多人版。
