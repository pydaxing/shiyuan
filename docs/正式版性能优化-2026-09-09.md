# 正式云端链路性能优化记录

## 范围与结论

本轮修的是请求数量、数据体积、缓存生命周期和图片处理，不是只换加载文案。云函数仍为 `kitchen-v2`，未购买/升级资源、未放开数据库权限、未取消内容审核或私有图片加密。代码和云端更新不等于微信公开发布，手机须使用本轮新预览包。

诊断表明慢来自多段叠加：重复请求、事务往返、文本/图片审核、SDK和网络，以及偶发冷启动。不能归结为“数据库性能不行”，也不能保证所有保存都瞬时完成。

## 已实施

- 广场首屏每页16条，数据库最多取17条判断是否还有下一页；游标续读，触底加载，保留失败重试按钮。列表只投影轻量卡片，完整食材与做法点开再取。新发布记录生成卡片，旧记录兼容按需补读，未批量迁移旧数据。
- 广场按家庭、类型、分类、搜索词缓存最近12组结果，30秒有效；切换后复用在途请求，离开页面后返回的结果可入缓存但不能覆盖新页面。完整空广场结果可复用于其他过滤条件，避免空库也连续读多次。过期缓存保留画面并后台刷新。
- 评论独立每页20条。发表、回复、点赞走增量变更；重试回执与过期家庭版本的回退也不再要求新客户端全量拉取评论。旧客户端保持兼容。
- 家庭开关立即显示最新意图，120ms合并窗口将三个设置合成一个请求；后端限流、幂等回执与家庭变更收敛到一个事务。失败提示并回退，未把乐观显示当作数据库已保存。
- 原生照片按最长边逐级缩小，最多5档，实际字节校验至480KiB以内才上传；长图不再仅限制宽度。整个应用共享最多2个压缩/上传任务。先显示本地缩略图和进度，部分失败保留成功图片，仅重试失败项。
- 列表封面和步骤图接近视区才申请解密图片；图片缓存最多100条、下载并发3，5分钟后重新鉴权；未变更文件只返回版本确认，不重复下载。保留失权清理和历史订单中图片的合法引用校验。
- 图片预览先解析真实可用路径，再打开轮播，避免未加载的懒加载图变成空地址。
- 分类统一为荤菜、素菜、汤羹、主食、小食、饮品、其他；首页/广场/创建页共用枚举。套餐不强行按单菜分类筛选；旧“其他”数据不自动猜测迁移。
- 新增可选菜谱来源对象，保存、编辑、分享、导入均保留，文字审核覆盖来源说明；详情页收纳在“来源与改编说明”中。来源字段不是平台权属认证。

## 同环境实测

证据：`artifacts/deployment/performance/optimized-production.json`。这是微信开发者工具调用真实云端，不是真机4G/5G或弱网结果；测量时本家庭菜谱、订单等业务列表为空，设置按原值提交。

- 三项开关合并保存：675、641、726ms；云端内部379、377、408ms。此前逐项保存每项约643–1066ms，三个连续调用会累计等待。合并请求和即时交互解决的是不同层的问题。
- 空广场大部分热请求381–579ms，云端内部约103–139ms。
- 一次明确 `firstInvocation=true` 的筛选请求2167ms，云端内部250ms。约1917ms不在业务计时内，可能包含SDK、传输、调度和初始化，不能全说成数据库耗时或精确归因为单一冷启动阶段。
- 家庭名称/封面文字保存1596、1286、1305ms，仍包括文本安全检查，不能宣传为即时落库。
- 去除启动公共广场预读后的bootstrap为520ms，云端内部183ms。

照片实验：`optimized-photo-compression.json`。两张是合成纹理PNG，不是真实相机照片；旧路径重新编码后曾达1,640,639/4,673,473字节，新路径分别394,418字节（800×1200，243ms）和33,350字节（327×1400，67ms）。本实验未上传云端，不是画质保证或照片端到端上传耗时。

## 菜谱批次

子Agent真实取得42条HowToCook候选文字及固定版本来源证据，另比较中文维基教科书、下厨房等来源。没有宣称抓遍全网，没有绕过403，没有下载权属未核实的39个图片引用。

3条经逐项文本/数量核对的改编版已通过正常 `saveRecipe` 审核链写入当前家庭并云端回读：韭菜炒蛋、紫菜蛋花汤（基础版）、小米粥（普通锅版）。未发布广场，未覆盖旧菜品。回执为 `artifacts/deployment/private-recipe-import-20260909.json`。

来源为HowToCook的Unlicense及明确涵盖菜谱文字的投稿声明；保留作者、固定版本链接和改编说明。不是逐作者权属担保，也未做真人试做。原料量不缩放，1/3/4人分餐依据及估计已留说明，接口默认元数据2不代表这些配方都是2人份。其余39条仍待处理数量缺失、表达歧义或第三方来源问题，不硬填“适量”为固定数字。

离线候选与验证入口：`artifacts/recipe-sources/README.md`、`scripts/import-recipe-candidates.mjs`。正式私家导入工具 `scripts/import-reviewed-private-recipes.mjs` 默认仅校验，只有显式 `--live` 才云写；已有回执拒绝重复执行。

## 验收与尚未解决的容量边界

- 最终 `npm run build:release` 309/309通过，执行全套业务回归、原生交互检查、真实微信产物ES5二次转译检查；不是仅测试未压缩源码。
- 离线菜谱转换器8项测试通过；主应用覆盖35条广场分页、45条评论分页、嵌套回复和重放、跨家庭鉴权、缓存失权、合并开关和照片失败重试。
- 模拟器受控夹具验证16→32→35条游标续读、详情展开和多步骤图布局；调用编译事件及滚动钩子，不代表真实手机触摸/滚动帧率。夹具只驻留运行时，未写云端，结束恢复真实接口。证据在 `artifacts/deployment/performance/community-ui-fixture.json` 和同目录截图。
- 尚未做大量真实用户压测。广场已分页，但已加载的卡片仍累积在页面内，不是无限长列表虚拟化；后续大流量需测长列表内存与回收策略。
- 家庭内业务仍按集合读成快照、写操作按依赖读取，家庭跨年大量历史订单需另做归档/时间段接口；本轮未假称已经完成。
- 搜索仍是转义且限长的数据库文本匹配，不是大规模全文检索；旧卡片补读和复杂过滤应在有代表性数据量时复测索引。
- 冷启动、审核耗时、实际手机相册权限、弱网和画质仍须真机复验。未以绕过审核、公开图片或购买常驻实例换速度。
