# 版本与发布

食愿从 `1.0.0` 开始作为首个正式推出的稳定版本。此前微信平台已上线 `0.6.1`，属于早期版本历史；2026 年 10 月 28 日误上传的 `0.6.0` 不应提交审核，须使用本次重新上传的 `1.0.0`。

## 编号约定

| 版本 | 用途 |
| --- | --- |
| `1.0.0` | 首个正式推出的稳定版本 |
| `1.0.1`、`1.0.2` | 问题修复、小范围体验调整 |
| `1.1.0`、`1.2.0` | 兼容现有使用方式的新功能 |
| `2.0.0` | 有明显不兼容变化的重大改版 |

主版本、次版本、修订号按数字比较；不能按字符串比较。次版本和修订号各限定为 0–99。内部 `versionCode = 主版本 × 10000 + 次版本 × 100 + 修订号`，例如 `1.0.0 → 10000`、`1.0.1 → 10001`、`1.1.0 → 10100`。

版本同时保持在 `package.json`、`package-lock.json` 的顶层与根包，以及 `src/manifest.json` 的 `versionName` / `versionCode` 中；不要替换依赖包自己的版本。上传命令自动从项目版本读取 `--upload-version`，不再手写另一个版本号。

## 上传前核对

1. 从微信公众平台版本管理页面或用户提供的当前截图核实线上版本，记录证据及时间，不能根据本地 `package.json` 猜测线上版本。
2. 统一修改上述版本配置，运行版本校验。新上传版本必须高于已核实的线上版本。
3. 按 `AGENTS.md` 构建、备份并验证 `dist/release`。保留正式 AppID、云环境、云函数及开发者工具配置。在微信开发者工具使用真实云数据验收。
4. 用户授权上传后使用下列命令。将 `--published-version` 换成当次核实的线上版本，不能长期沿用示例值。

```sh
npm run release:check -- --published-version 0.6.1
npm run release:upload -- --published-version 0.6.1 --desc '1.0.0 正式版：完善家庭管理与清理，统一食材用量，优化菜单、美食和分享体验。'
```

`release:upload` 校验源码版本一致性、版本递增、已编译的 `appVersion` / `appVersionCode` 和 `verifyPreviewTarget` 后才会调用微信上传，回执保存在 `artifacts/uploads/`。版本校验不代替构建与真实页面验收。

上传、提交审核、审核通过、正式发布分别记录。只有平台明确显示正式发布成功，才能称为小程序已上线；云函数部署也单独记录。
