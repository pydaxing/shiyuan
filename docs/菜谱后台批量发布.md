## 旧流程：为什么不能把草稿直接标成公开

`imports` 中的来源草稿保存的是已校验的归档、图片映射和来源审核，不等于微信内容安全检查已经完成。部分图片此前只在本地，直接改 `status` 会产生缺图或绕过检查的公开帖子。

旧流程通过微信客户端逐菜执行保存、分享、清理，重复审核文字/图片，并多次传输文件。这次增加受限的后台导入任务，管理员一批准备、一批执行、一批写入广场；不创建临时家庭菜品。

## 旧审核流程

1. 从云端读取已公开帖子与来源草稿，按来源 URL 和实际食材/步骤去重；核对本地归档、图片摘要、最新简洁菜名及类目。保留同名不同做法。
2. 用受授权的官方 CloudBase CLI 在仅服务端可写的 `imports` 集合登记导入授权和不可变任务。限定微信用户、家庭管理员、目标环境及 24 小时有效期；普通客户端不能生成授权。
3. 合并本批完整公开文本，按接口上限切分，不截断、摘要化或省略文字。所有文本任务通过才处理图片；安全检查额度不足立即停止。
4. 用官方云存储批量上传归档文件。已确认且摘要一致的图片复用；新图片在云函数中核对文件字节并逐张审核，然后加密保存高清/列表/详情三种版本。不向客户端返回密钥。
5. 回读全部任务和图片回执，核对内容摘要、来源版本和媒体归属。按现有分享模型构造帖子、卡片、搜索字段及来源记录，按请求字节上限分批 `INSERT` 到 `posts`，不覆盖现有帖子。
6. 逐条回读检查名称、类目、用料、完整步骤、图片顺序及卡片。确认成功后更新本地发布回执，并关闭本批临时授权。历史草稿保留用于溯源，不代表仍待发布；实际公开状态以 `posts` 和发布回执为准。

批量是一次逻辑任务，不把超过平台请求限制的所有 JSON 塞入一次网络调用。各分批都有写入意图、确定性帖子 ID 和回执；部分失败时保留成功结果，只恢复缺项。

## 核验依据

- `plan.json`：完整来源、原文/图片摘要、文本分块、目标家庭和环境。
- `prepare-*.json`、`publish-*.json`：每批写入意图及官方回执。
- `upload-output.txt`：批量原文件传输结果，不等同于审核完成。
- `processing.json`：真实微信调用的文本/图片处理进度。
- `quota-blocker.json`、`blocked-audit.json`：服务额度阻塞及数据库实际状态，不代表已公开。
- `publish-intent.json`：经过回执核验的最终帖子内容。
- `verified.json`、`posts-after.json`：最终回读数量与完整内容。

后台临时原文件只用于本批转存。成功后按 `plan.json` 中唯一的 `authorized-import/<任务标识>` 前缀清理，不清理 `approved/`、其他任务前缀或本地来源归档。
