# 通用菜谱导入

`scripts/generic-recipe-import.mjs` 是新增数据的通用契约，不限定来源网站、名称或数字形式的来源 ID。历史 `normalize-authorized-recipes.mjs` 等脚本专门服务当时的下厨房批次，保留用于回溯，不是新来源的入口，不能直接重跑。

适配器负责将任意已获使用授权的数据整理为标题、分类、时长、份数、封面、食材、步骤。将稳定的 `identity`（例如来源命名空间加记录 ID）与公开内容分开传入；由模块生成确定性 ID。原始 JSON、许可、图片哈希、修订记录、标签等放入私有导入档案。

`publicRecipe` 使用字段白名单，公开记录不包含来源名称、链接、来源说明或原始元数据。模糊用量只接受「适量」「少许」，其他食材必须提供数字 `quantity` 与项目支持的 `unit`。复合食材需要适配器拆分，缺失信息不能编造精确数字。封面和步骤图片必须解析到已上传的云文件。

正文也需要清理：`publicCookingText` 去掉独立参考资料、视频链接和上游项目的 Issue / Pull request 提示，保留实际烹饪内容。适配器应把参考说明与操作步骤分行保存，并在发布前扫描最终正文；不能只删除 `provenance` 字段就认定来源已经隐藏。原文始终留在私有档案中。

步骤只承载实际烹饪操作，不能把菜品介绍、食材清单的补充说明包装成步骤。`isCookingStep` 在公开数据出口排除「菜品介绍」「备料说明」及其数字分段；菜品简介使用简介字段，食材仍使用结构化清单。清洗前的说明保留在私有档案，不能再次拼接进步骤。

`buildGenericPost` 统一生成「食愿小灶」官方发布卡片。`importedAt` 是真实导入时间；兼容现有云端按 `createdAt` 排序的实现，`createdAt` 与 `publishedAt` 使用明确指定的展示时间。`interleavedDates` 将新记录插入已有发布时间区间，不覆盖旧记录。这个展示时间不代表历史上实际发布过，导入审计必须记录分散展示的策略。

导入执行器应逐阶段保存计划、备份、媒体上传回执、数据库写入意图和回读证据。使用确定性 ID、只插入缺失且完全一致的记录，不覆盖同 ID 的其他内容。图片兼容现有加密媒体协议，生成原图、卡片和详情版本；上传后逐文件核对大小与摘要，再插入媒体和公开菜品记录。数据库请求应限制在 85 KB 内，避免大请求失败。

文字和图片检查要如实记录，不得套用历史批次的「用户已逐项审阅」或平台安全检测通过声明。导入完成后使用本项目 `dist/release` 在微信开发者工具中核验真实云端数据。运行单元测试或本地生成文件不等于线上发布。

本次参考适配器和运行回执位于本机忽略目录 `artifacts/vibecook-import-20261028/`。原始数据与加密密钥不进公开 Git 仓库。跨电脑运行需另行取得这些档案及云端权限。
